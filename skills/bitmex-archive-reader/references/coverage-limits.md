# ⚠ 覆盖局限 —— 动数据之前必读

**这份档案最容易被误用的方式，是拿它回答它答不了的问题。**

本文档全部依据 `manifest.json`（`spec_version 1.1`）的实测字段与统计值，以及三个终端快照的实读结果。

## 一、生命周期事件几乎不存在

| `execType`（`execution.csv`） | 次数 |
|---|---|
| `Trade` | 160,642 |
| `Funding` | 12,916 |
| `Settlement` | 19 |
| `New` | **8** |
| `Replaced` | **6** |
| `TriggeredOrActivatedBySystem` | **1** |
| `Canceled` | **0（API 未返回）** |
| `Rejected` | **0（API 未返回）** |

manifest 字段：**`complete_historical_lifecycle_guaranteed: false`**
`lifecycle_event_count: 15`，时间范围仅 **2025-06-13 → 2025-06-19**（6 天）。

### 由此**不可计算**的指标

| 想算 | 为什么不行 |
|---|---|
| 撤单率 / 撤单次数 | `Canceled` 返回 0 条 |
| 拒单率 | `Rejected` 返回 0 条 |
| 订单存活时长 | 需要 `New` 与终态的时间戳，`New` 只有 8 条 |
| 改单习惯 | `Replaced` 只有 6 条 |
| 挂单成交率 | 需要完整的下单/成交事件对 |

### ⚠ 缺失 ≠ 未发生

上游在 README 中明确写过这一点，此处转述其含义：
**API 返回了什么就发布什么，不合成缺失事件，也不从订单快照反推时间戳。**
所以「0 条撤单记录」的正确解读是「**这份导出不包含撤单事件**」，
**不是**「这个账户从不撤单」。

**如果你要回答与订单生命周期有关的问题 → 这份数据不够，必须另取源。**

## 二、`order.csv` 是终态快照，不是过程日志

43,258 行，每行 = 一个 `orderID` 的**最新返回状态**。

- `ordRejReason` 列存在，但绝大多数为空
- 想看订单「中途经历过什么」→ **做不到**
- `execution.csv` 里的 `ordStatus` 是**成交发生当时**的状态，与 `order.csv` 的终态**可能不同** —— 这是正常的，不是冲突

## 三、快照非原子，跨表时间错位

`manifest.source_export.snapshot_consistency`：
`Sequential API reads, not an atomic account snapshot`

| 快照 | 读取时刻 |
|---|---|
| margin（BMEx） | 2026-07-23T09:07:47.913Z |
| margin（USDt）/ wallet（USDt） | 2026-07-23T10:00:39.900Z |
| margin（XBt）/ wallet（XBt） | 2026-07-23T12:56:05.357Z |

**最大错位 3 小时 48 分。** 跨快照做加减（如「持仓 + 钱包 = 权益」）会引入这个误差。

### 另外两个时序陷阱

| 陷阱 | 说明 |
|---|---|
| `user-wallet.snapshot` 只覆盖 **2025-11-25 起** | 15 行里大量 alt 币为 0。**不能用它算历史累计出入金** |
| **账本最后事件 2026-07-23，导出 2026-09-11** | 中间约 **7 周活动不在档案里**。这不是"截至今天"的镜像 |
| `instrument` 表 `first_time` = 2014-11-21 | 含 2020 前已下架合约，按 `symbol` join 可能匹配不上 |

## 四、两个财富口径不可混用

| 口径 | 列 | 本 build 状态 |
|---|---|---|
| 钱包等价财富 | `adjustedWealthXBT` | ✅ 有值：**99.46454272 XBT / 54.070351×** |
| 标记市值 | `adjustedMarkedWealthXBT` | ⚠ **manifest 汇总为空 —— 未计算** |

**钱包等价**已扣除后续入金、加回后续出金、中性化内部划转。
**它不是 mark-to-market NAV**，也不含未实现盈亏。

→ **报业绩只能用 `adjustedWealthXBT`，并注明是钱包等价口径。**
→ 不要把 54.07× 描述成"净值"或"账户总资产"。

## 五、这份数据明确不包含的东西

上游声明**有意不发布**：

- 原始 API 密钥
- `/api/v1/user` 账户资料
- 客户端自设的订单标识（`origClOrdID` / `clOrdID` / `clOrdLinkID` / `brokerLinkID`）
- 未审阅的执行自由文本字段（`text` / `ordRejReason` / `error` / `algoOrderDetails`）
- 登录 / IP / 设备 / 资料数据
- 钱包历史的链上 tx hash

`tradeHistory.csv` **保留**了 `text` 列（因为它有助于解释成交、资金费与结算），
但其中的非 BitMEX 主机名**已脱敏**。

**→ 追不到链上、追不到设备、追不到真实姓名。这是有意的隐私边界，不是数据缺失可以补的。**

## 六、方法学边界（作者自己划的）

- **不是** HFT 数据集
- **不是** CLOB（订单簿）微观结构数据
- **不是** 毫秒级价格预测数据
- 定位是「**手工、自主、图表驱动的 BTC 交易的带时间戳档案**」—— 关注的是仓位管理、风险控制、回撤处理、长期复利

**衍生权益曲线**只追踪 XBT + USDt 两个钱包，
**不是**覆盖 BitMEX 历史上所有非 XBT 钱包与资产的历史 NAV。

## 七、结论必须标注确定度

| 层级 | 示例 | 标注 |
|---|---|---|
| 档案直接给出的 | 行数、时间范围、`execType` 分布、sha256 | **[已证实]** |
| 由档案聚合得出 | 某年成交笔数、持仓时长分布、资金流 | **[有证据]**（附聚合口径） |
| 从缺失推断 | 「此账户不撤单」 | **❌ 不可断言** |
| 引入外部数据 | 与同期 BTC 价格对比、收益率计算 | **[有证据]**（须标注另取的数据源与时点） |

**档案本身已声明：任何长期结果都包含时机与运气。**
本档案的价值是「**在结果揭晓之前就已公开的轨迹**」，
**不是**「可复制的盈利方法」。

**→ 任何从这份数据推出的策略结论，都必须先做样本外与样本内分离，并明确写出它只有 n = 1。**
